# Эталонный набор

Кейсы для `make eval`. Схема описана в `evals/dataset.py`, загрузчик там же: он отвергает лишние поля и повторяющиеся `id`.

| Файл | Что проверяет | Сколько |
|---|---|---|
| `howto_config.yaml` | поиск и ответы: «как сделать» и «что настроить» | 20 |
| `out_of_scope.yaml` | честный отказ: ответа нет ни в документации, ни в коде | 12 |
| `holdout/holdout.yaml` | отложенная выборка: 6 howto, 4 config, 8 out_of_scope | 18 |
| `errors.yaml` | разбор ошибок: текст ошибки или строка лога → место в коде (`expected_line`) | 30 |
| `holdout/errors.yaml` | отложенная выборка ошибок | 15 |
| `error_reports.yaml` | разбор ошибок, как их присылают люди: строки лога, ошибки задач, пересказы | 12 |
| `changelog.yaml` | устаревший changelog: старая запись, которую позже отменили (`stale_line` → `current_line`) | 13 |
| `judge/canaries.yaml` | проверка модели-судьи: утверждение, фрагмент, правильный вердикт | 12 |
| `judge/clarity_canaries.yaml` | проверка судьи по грамотности: смысл подтверждён, текст хороший или плохой | 12 |

`make eval` читает только `*.yaml` в корне каталога. Отложенную выборку смотрят один раз, когда модель и промпт уже выбраны: иначе она перестаёт быть независимой оценкой. У канареек свои схемы (`Canary` и `ClarityCanary` в `evals/dataset.py`).

## Как получен `howto_config.yaml`

Чтобы набор не подгонялся под поиск, кейсы писал **отдельный субагент без контекста разработки**:
- кода поиска, тестов и результатов он не видел;
- в его распоряжении были только документация Paperless-ngx v3.4.2 и список разделов с идентификаторами.

Порядок работы:
1. Промпт субагента (ниже) автор проекта увидел и одобрил до запуска.
2. Нарезчик документации выдал список разделов, которые становятся кусками (без changelog): `id`, файл, строки, путь заголовков. Только из этого списка субагент брал `expected_sources`.
3. После субагента проверялись только схема и существование каждого `id`. Содержание кейсов вручную не правилось.
4. Набор закоммичен раньше, чем появился код поиска: это видно в истории git.

Пометки субагента:
- Ограничение «не больше 6 кейсов на файл» он считал по первому источнику кейса. Если считать дополнительные источники, `usage.md` и `configuration.md` встречаются по 8 раз.
- `must_include` в howto-кейсах — короткие русские формулировки фактов. Их нужно проверять по смыслу, а не подстрокой. В config-кейсах это точные имена параметров.
- Документация v3.4.2 местами противоречит сама себе. Пример: значение `PAPERLESS_TASK_WORKERS` по умолчанию в `setup.md` и в `configuration.md` указано по-разному. На кейс config-007 это не влияет.

## Как получены `errors.yaml` и `holdout/errors.yaml`

Эти наборы не пишет субагент — их генерирует `evals/generate_errors.py` из исходников тега (сид фиксирован, вручную не правятся, при смене тега генерируются заново). Правильное место ошибки известно автоматически: строка кода, где задан её текст.

- Берутся видимые пользователю сообщения: `_fail` обработчика документов, error и exception логгера, warning, `raise`; без debug и info. Шаблоны, которые встречаются в коде дважды, не берутся: их место неоднозначно.
- Поровну по видам, не больше 3 из одного файла; dev и отложенная выборка не пересекаются.
- Подстановки заполняются правдоподобными значениями (`scan_0042.pdf`, `42`, `[Errno 13] Permission denied`), текст оборачивается так, как его присылают: голое сообщение, строка лога с префиксом, ошибка задачи `файл: сообщение`, вопрос по-русски, обрезанное сообщение.

**Слабое место.** Генератор и точный поиск видят одни и те же шаблоны (`assistant/indexing/messages.py`): если извлечение пропускает какой-то вид сообщений, генератор такой кейс не создаст. Поэтому рядом есть кейсы независимого субагента (`error_reports.yaml`), а в паспорте индекса — покрытие извлечения (на v3.4.2 шаблон извлечён у 739 из 833 вызовов).

- В 002, 003, 009 и 012 вставленный текст содержит ещё и общее сообщение-обёртку из другого места («Error occurred while consuming document …»). Правильное место — то, где задаётся конкретный текст.
