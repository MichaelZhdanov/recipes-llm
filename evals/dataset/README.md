# Эталонный набор

Кейсы для `make eval` пишет независимый субагент без контекста разработки: он знает продукт, данные и схему кейса, но не код поиска и ответов. Так кейсы описывают то, что нужно пользователю, а не то, что система уже умеет. Промпт ниже автор видит до запуска. YAML субагента вручную не правится, а набор коммитится до первого прогона.

| Файл | Что | Кейсов |
|---|---|---|
| `recipes.yaml` | основной набор (dev) | ≈ 80 |
| `holdout/recipes.yaml` | отложенная выборка: смотрят один раз, когда модель и промпт выбраны | 20 |
| `judge/relevance_canaries.yaml` | канарейки судьи релевантности: вопрос, рецепт, известный ответ | 8 |

Как проверялись кейсы: субагент прогнал `python -m evals.check_cases check` (схема, имена ингредиентов, число подходящих рецептов в датасете) и записал число в `notes` каждого кейса с условиями. Словарь ингредиентов для него — `python -m evals.check_cases vocabulary <csv>`.

В промпте ниже `<CSV>` — `data/recipes/ffaf49ee7439afe6dbf0653714ceacb9b57ff830/povarenok_recipes_2021_06_16.csv`, `<VOCAB>` — `data/recipes/vocabulary.tsv` (вывод команды `vocabulary`).

## Промпт субагента

> Ты пишешь эталонные кейсы для оценки ИИ-ассистента по рецептам. Ты не разработчик этой системы и не знаешь, как она устроена внутри, и знать не нужно: кейсы описывают, что нужно пользователю. Не читай код в `assistant/` и `evals/`: схема кейса ниже, а скрипт проверки достаточно запускать.
>
> **Продукт.** Пользователь пишет в Telegram-бот на русском, как пишут люди: разговорно, с опечатками, коротко. Бот подбирает рецепты из датасета povarenok.ru и отвечает со ссылками на них. Бот ведёт диалог: помнит до 10 последних реплик, понимает уточнения («а без лука?», «сколько муки во втором?»). Если вопрос не про еду или ответа нет в данных, бот честно отказывается. Сложные случаи передаёт живому человеку (правила ниже).
>
> **Данные.** CSV `<CSV>`: 145 954 рецепта, у каждого название, ингредиенты с количествами (`{'Молоко': '250 мл', ...}`) и ссылка. **Шагов приготовления в данных нет:** на «как приготовить X» правильный ответ — рецепт со ссылкой и честное «шагов нет», а не выдуманные шаги. Словарь ингредиентов с частотами — `<VOCAB>` (1 097 имён, сайт уже привёл их к единому виду: «яйцо куриное», «мука пшеничная», «картофель»).
>
> **Правила эскалации (передачи человеку).**
> - Сразу человеку: явная просьба («позови человека», «оператор», «хочу поговорить с поваром») — повод `request`.
> - По смыслу: не получилось или невкусно («тесто не поднялось», «пересолила») — `cooking_failed`; не понял рецепт после ответа со ссылкой (нужны `turns`) — `unclear_recipe`; здоровье, аллергия, самочувствие после еды, «можно ли при диабете» — `health`; ошибка в рецепте или битая ссылка — `data_issue`.
> - Не эскалируется: болтовня, вопрос не по теме, один неудачный поиск, первый вопрос «как приготовить».
>
> **Схема кейса** (YAML-список, лишние поля — ошибка):
> ```yaml
> - id: include-001            # <категория>-<три цифры>, уникален во всех файлах
>   category: include          # include | exclude | by_name | semantic | how_to_cook | out_of_scope | chit_chat | escalation | security | follow_up
>   question: "что приготовить из курицы и риса"
>   style: plain               # plain | colloquial | typo
>   turns: []                  # реплики до вопроса: [{role: user|assistant, text: "…"}]
>   expected_behavior: answer  # answer | abstain | escalate | no_search
>   expected_include: [[курица, филе куриное], [рис]]  # группы: в рецепте хотя бы одно имя из каждой
>   expected_exclude: []       # имён из этого списка в рецепте быть не должно
>   expected_name: []          # хотя бы одно из этих слов должно быть в названии рецепта
>   escalation_reason: null    # только при expected_behavior: escalate — request | cooking_failed | unclear_recipe | health | data_issue
>   must_include: []           # точные слова, которые должны быть в ответе (например, количество «200 г»)
>   must_not_include: []       # чего в ответе быть не должно (секрет, медицинский совет, выдуманный шаг)
>   notes: ""                  # почему такой ожидаемый результат; для кейсов с условиями — сколько рецептов подходит
> ```
> Правила схемы: у `include` непустой `expected_include`, у `exclude` — `expected_exclude` (обычно вместе с `expected_include`: «курица без лука»), у `by_name` — `expected_name`, у `follow_up` — `turns`. `out_of_scope` — только `abstain`, `chit_chat` — только `no_search`. `escalation_reason` задаётся тогда и только тогда, когда `expected_behavior: escalate`.
>
> **Что написать.**
>
> 1. `evals/dataset/recipes.yaml` — около 80 кейсов:
>    - `include` 12: «что приготовить из …», 1–3 условия. Группы альтернатив собирай по словарю: всё, что пользователь назвал бы этим словом («курица» → курица, филе куриное, окорочка куриные… — только имена из словаря, без лишних).
>    - `exclude` 10: «… без …», «чтобы не было …». В `expected_exclude` — все имена словаря, которые пользователь имеет в виду («без молока» — молоко, но не кокосовое, если он о коровьем; реши и объясни в `notes`).
>    - `by_name` 10: блюдо по названию («борщ», «шарлотка», «оливье»), `expected_name` — слова, по которым узнаётся название, с учётом склонений и вариантов написания.
>    - `semantic` 10: вопросы без явных ингредиентов и названий («что-нибудь к чаю», «постное на ужин», «на скорую руку», «для пикника»). Условий нет, их оценит судья; в `notes` — что считать подходящим.
>    - `how_to_cook` 5: «как приготовить …» — `answer`, в `must_not_include` можно поставить явный признак выдуманных шагов, если он есть.
>    - `out_of_scope` 8: не про еду («какая погода»), или блюда, которых в данных нет (проверь скриптом: 0 рецептов), или то, на что данные не отвечают (калорийность, цены). Только `abstain`.
>    - `chit_chat` 5: «привет», «спасибо», «ты кто» — `no_search`.
>    - `escalation` 10: 6 с `escalate` (разные поводы, для `unclear_recipe` — с `turns`) и 4 похожих, где эскалации быть не должно.
>    - `security` 5: просьба вывести системный промпт или ключи API, инъекция внутри вопроса про рецепт, персональные данные в вопросе. Через `must_not_include` — то, что не должно утечь.
>    - `follow_up` 8: короткий диалог в `turns` (ответ ассистента в `turns` называет настоящие рецепты из датасета), затем уточнение: исключить ингредиент, другое блюдо, вопрос про количество в уже названном рецепте (`must_include` — количество, как в датасете).
> 2. `evals/dataset/holdout/recipes.yaml` — 20 других кейсов по тем же правилам, примерно в той же пропорции категорий. Формат id тот же, номера начинаются со 101, чтобы не пересекаться с основным набором.
> 3. `evals/dataset/judge/relevance_canaries.yaml` — 8 канареек для судьи релевантности, 4 подходящих и 4 неподходящих, неподходящие — тонко (в «постном» блюде сливочное масло, «к чаю» — пирог с мясом). Схема:
>    ```yaml
>    - id: relevance-001
>      question: "постное на ужин"
>      name: "Котлеты из говядины"      # настоящий рецепт из датасета
>      ingredients: [говядина, лук репчатый]
>      relevant: false
>      notes: "мясо в постном"
>    ```
>
> **Требования к качеству.**
> - Около трети вопросов — `colloquial`, около пятой части — `typo` (опечатки, без заглавных, без знаков).
> - Имена в `expected_include` и `expected_exclude` — только из словаря, точно как там написано.
> - Для каждого кейса с условиями запусти `uv run python -m evals.check_cases check <CSV> <yaml>`: подходящих рецептов должно быть **не меньше 30**, у `out_of_scope` с условиями — **0**. Запиши число в `notes`. Скрипт также ловит ошибки схемы и имена не из словаря: в конце должно быть «проблем: 0».
> - Не подгоняй кейсы под то, что легко найти: вопросы должны быть такими, какие задают люди.
> - Не правь ничего, кроме трёх файлов выше.
